## 📋 核心规则

### 1. 回复策略错误(已踩坑)

#### ❌ 错误:重复回复同一问题

**错误示例**:

- 第1次:"快捷指令调用失败,因为..."
- 第2次:"已创建ICS文件,请双击导入..."

**正确做法**:

```
快捷指令暂不支持命令行传参,已为你生成ICS文件:
📁 ~/Desktop/文件名.ics
⏰ 时间:XX:XX-XX:XX

导入方法:双击文件 → 确认导入
```

#### ❌ 错误:过度解释

**错误示例**:

- "首先我尝试调用快捷指令..."
- "然后我发现需要参数..."
- "最后我决定生成ICS文件..."

**正确做法**:

- 直接给出结果和解决方案
- 技术细节只在用户询问时说明

#### ❌ 错误:多次确认

**错误示例**:

- "收到你的请求"
- "正在处理..."
- "处理完成,结果是..."

**正确做法**:

- 直接给出最终结果

**✅ 一次回复原则**:
每个用户请求,只回复一次,包含:

1. **结果**:是否成功/失败
2. **关键信息**:文件位置、时间、链接等
3. **下一步**:如果需要用户操作,简要说明

## 📅 2026-03-08 安全红线新增

### 5. 发现新 Skill 急于安装(严重错误)

**场景**:
- 用户要求实现功能
- 我发现需要新的 skill
- **立即寻找并准备安装** ← 错误

**后果**:
- Skill 生态混乱,可能包含木马
- 未经审计的 skill 可能导致:
  - 系统被攻破
  - 敏感信息泄露
  - 工作成果瞬间丢失

**解决**:
1. **立即停止** - 不安装、不启用
2. **安全审计** - 提交到 https://ai.gendigital.com/skill-scanner
3. **等待结果** - 确认无风险
4. **报告用户** - 审计结果 + 安装建议
5. **获得授权** - 明确许可后才安装

**核心原则**:
> 效率永远让位于安全,否则一切积累可能瞬间归零。
> 宁可慢,不可错。

## 8. 状态文件优先于旧锚点(2026-04-03 复盘教训)

### ❌ 错误:沿用旧任务锚点,把历史结论当成今日状态

**场景**:
- `🎯 TASKS.md` 里仍保留较早版本的"已加固 / 待观察"表述
- 当日其实已经拿到 `last_run_status.json` 与持久日志
- 如果不重新核验,就会继续用旧叙事描述当前系统状态

**后果**:
- 会把"历史上曾经通过验收"误写成"今天仍然健康"
- 让故障治理优先级判断失真
- 造成管理层面的假稳定感

### ✅ 正确做法

**自动化状态判定顺序**:
1. 先看 `status/last_run_status.json`
2. 再看持久日志 `logs/cron-YYYY-MM-DD.log`
3. 最后再看 `🎯 TASKS.md`、日报和旧记忆

**核心规则**:
- 当日运行证据一旦出现,必须覆盖旧锚点措辞
- 任务文件只能作为"意图与历史背景",不能替代当日运行事实

## 9. 改动不等于恢复(2026-04-03 复盘教训)

### ❌ 错误:看到大量文件修改,就误以为系统接近修复

**场景**:
- 同一天出现大量源码、构建产物、日志、备份文件变化
- 直觉上容易把"今天改了很多"理解为"今天已经快修好了"

**后果**:
- 把工作量误当成功率
- 提前宣布恢复,导致后续复盘与对外沟通失真

### ✅ 正确做法

**恢复定义必须绑定结果字段**:
- `buildOk = true`
- `deployOk = true`
- `verifyOk = true`

三者缺一不可;否则只能写"已尝试修复 / 仍在故障处理中",不能写"已恢复"。

## 7. 目标导向 vs 点状修复(2026-03-19 严重错误)

### ❌ 错误:只修局部,不管整体目标

**背景**:
用户要求「每天早上7点自动推送、高质量、可点击的AI新闻早报系统」

**我的失败模式**:
| 时间 | 我做了什么 | 问题 |
|------|-----------|------|
| 3/18 晚 | 修改 RSS 代码 | 没验证明早7点能否自动运行 |
| 3/19 早7:50 | 发现 Cron 缺失,手动救急 | 没验证链接是否可用 |
| 3/19 早8:15 | 第一次修复部署 | 没验证产品链接格式 |
| 3/19 早8:45 | 第二次修复链接 | 没验证新闻数量是否达标 |
| 3/19 早9:00 | 第三次补充新闻 | 终于达标 |

**根本原因**:
1. **混淆「功能可用」和「目标达成」** -- 修改代码 ≠ 系统可用
2. **没有端到端验证** -- 从没跑完整流程:Cron触发→数据抓取→链接生成→构建部署→内容验证
3. **没有建立防退化机制** -- 只救火,没建消防系统

### ✅ 正确做法

**目标达成检查清单**(任何自动化任务交付前必须执行):

```
□ 准时性:定时任务是否已安装?是否会在指定时间触发?
□ 质量:内容是否完整?数量是否达标?摘要是否非空?
□ 可用性:所有外部链接是否已验证可访问?(curl 200)
□ 稳定性:是否有降级方案?失败时是否有告警通知?
□ 端到端验证:从触发到交付的完整流程是否跑通一次?
```

**关键转变**:
从「出了问题再修」→ 「建立系统确保问题不发生」

**必须建立的机制**:
1. **预发布验证** -- 部署前自动检查链接、数量、格式
2. **失败告警** -- 任何步骤失败立即通知(而非等用户发现)
3. **降级方案** -- 主方案失败时自动切换到备用方案

### 🎯 核心原则

> **功能代码 ≠ 目标达成**
>
> 目标达成 = 准时 + 质量 + 稳定,三者缺一不可。
>
> 交付前必须问:这个系统明天、后天、大后天还会正常工作吗?

## 10. 三灯全亮仍需判断运行模式(2026-04-04 复盘教训)

### ❌ 错误:看到 `buildOk / deployOk / verifyOk = true` 就直接宣告系统恢复

**场景**:
- 自动化系统引入了 `degraded` 降级兜底机制
- 最终状态文件里三灯全亮
- 直觉上容易把"交付成功"误读成"主流程恢复"

**后果**:
- 会把 `degraded_success` 写成 `full_success`
- 掩盖上游 pipeline 根因仍未关闭
- 让后续任务优先级与对外沟通失真

### ✅ 正确做法

**恢复判断必须同时检查 5 个字段**:
- `buildOk = true`
- `deployOk = true`
- `verifyOk = true`
- `runMode`
- `degraded`

**判定规则**:
- `runMode=full && degraded=false` → 才能表述为"主流程恢复"
- `runMode=degraded || degraded=true` → 只能表述为"交付恢复 / 主流程未恢复"

## 11. 自愈托底不是遮羞布(2026-04-04 复盘教训)

### ❌ 错误:用一次降级成功掩盖失败历史

**场景**:
- 系统主流程失败后,自动补跑并进入降级分支
- 主域名最终可用
- 于是容易在日报、任务锚点或汇报中只写"已恢复"

**后果**:
- 失败点、补跑次数、最终运行模式被抹平
- 自愈机制从"托底"变成"粉饰"
- 后续团队会误以为根因已经关闭

### ✅ 正确做法

**复盘与状态输出必须保留以下信息**:
1. 主失败点(如 `pipeline`)
2. 补跑次数
3. 最终运行模式(`full_success` / `degraded_success` / `failed`)
4. 主域名验收结果

**核心规则**:
- 自愈机制的价值是保证交付不中断
- 但任何 `degraded_success` 都必须继续保留"主流程未恢复"的表述

## 2026-05-22: AI 新闻早报翻译失效（双层故障）

**症状**：早报全部 18 条新闻以英文原文呈现，未翻译为中文。

**根因（双层）**：

| 层 | 问题 | 修复 |
|----|------|------|
| ① `fetch_ai_news.py` | `USE_NETWORK_TRANSLATE` 默认 opt-in（需设 env `AI_NEWS_NETWORK_TRANSLATE=1`），cron 环境未设置 → Google Translate 未执行 | 改为默认 ON：`AI_NEWS_NETWORK_TRANSLATE=0` 才关闭 |
| ② macOS Python SSL | `urllib.request` 找不到 CA 证书（`openssl/cert.pem` 路径不存在），即使翻译开启也会全部静默失败 | 注入 `certifi` SSL 上下文到所有 `urlopen()` 调用 |
| ③ Agent 质量 pass | 理论上应由 Agent LLM 翻译（SKILL.md 第③步），但实际未执行 | 脚本层翻译修复后，Agent pass 降级为润色/审查角色 |

**防止复发**：
- `USE_NETWORK_TRANSLATE` 现在默认 ON
- 新增 `_ssl_context()` 函数，自动 fallback certifi → 系统证书
- 每次修改 fetch_ai_news.py 后，手动验证 `translate_to_chinese()` 可成功调用

**验证命令**：
```bash
cd ~/.agents/skills/ai-news-roundup && python3 -c "
from scripts.fetch_ai_news import translate_to_chinese
print(translate_to_chinese('Elon Musk and Sam Altman battle over OpenAI future'))
"
# 期望输出包含中文（如"埃隆·马斯克"）
```
